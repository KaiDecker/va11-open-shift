# OPEN SHIFT 路线图

## 阶段 20：首个公开预览版（已完成）

- 全面更新公开文档、安装说明、贡献指南和发布清单；
- 增加可重复的自动检查与发布包审计；
- 完成全新用户安装、连续两天、保存/读档、卸载和 Steam 原版哈希验收；
- 发布 Windows x64 Preview，并邀请 Issue 和 PR。

## 阶段 21：原版风格与对话质量（已完成）

- 建立角色事实、关系和语气约束；
- 使用原版流程节奏作为结构参考，避免角色身份和语气错误；
- 增加对白自然度、重复内容和立绘连续性检查。

## 阶段 22：Agent 世界深化（已完成）

- 扩展记忆、目标、关系和跨日事件；
- 保持角色信息隔离，避免模型全知；
- 让事件对后续酒吧对白和平板内容产生可追踪影响。

阶段 22 的记忆系统使用 SQLite 内的角色私有记忆。每条记忆标记来源（亲历、听说、传闻、推断）、
可信度、可见性和归档状态；检索只返回当前角色在当前时间点可知且未归档的有限内容。旧数据库会在
启动时自动补齐字段，旧记忆按 legacy 来源读取。日志只记录角色、记忆 ID、来源、检索结果和归档数量，
不记录 API Key、提示词或完整响应。关系、目标、金钱和剧情游标仍由规则层维护，LLM 不能直接修改。

## 阶段 23：轻量安装与版本隔离（已完成）

- 不再复制完整 Steam 游戏目录；实例只保存补丁后的 `data.win`，只读资源使用 Windows 链接；
- 每个安装版本独立保存数据库、日志、配置、API Key 和 OPEN SHIFT 配套存档；原版 GameMaker 存档保持兼容；
- 安装状态记录实例 ID、补丁指纹和链接清单，升级不会误用旧实例；
- 卸载只删除当前实例及其链接，拒绝触碰 Steam 原版目录；
- 默认安装目录按 `PACKAGE_MANIFEST.json` 的版本命名为 `%LOCALAPPDATA%\OpenShift-<package_version>`；
- 同卷文件优先使用 HardLink，目录使用 Junction，跨卷文件使用 SymbolicLink；文件链接权限不足时逐个复制 EXE/DLL 并记录 `copied_file`，目录无法创建 Junction 时明确停止；
- 更新安装说明、玩家包说明和安全回退测试。
- 开发构建阶段使用 UTMT 生成 `patch/data-win.delta`；玩家端只应用带原版/目标 SHA-256
  校验的增量补丁，发行 ZIP 不包含 UTMT 或完整 `data.win`。

## 阶段 24：启动器与社区体验（已完成）

- 迁移到不携带 .NET runtime 的 Win32 + WebView2 原生宿主；
- 采用黑底、深紫硬边框和像素字体的 VA-11 HALL-A 风格启动界面；
- 增加更新检查、日志导出、一键修复和版本诊断；
- 改善生成模式、耗时和错误提示；
- 根据社区反馈迭代安装和贡献流程。

## 阶段 25：公开预览版发布准备（已完成）

- 统一公开版本号为 `v0.24.0-preview`，并准备对应的 GitHub Release 说明；
- 完成全新机器安装、API Key 保存、世界状态准备、启动、重启和卸载验收；
- 核对 GameMaker 临时运行配置路径修复，避免本地服务已启动但游戏无法读取连接信息；
- 对玩家 ZIP 做轻量包审计，确保不包含 UTMT、完整 `data.win`、源代码、数据库、API Key 或验收素材；
- 同步安装文档、发行清单和社区更新文案，明确旧 `v0.19.0-rc.23` 已过时。

## 阶段 26：持续城市事件与社区反馈（已完成）

- 建立 DAY2 至 DAY12 的代码拥有公共城市事件候选池，让每个营业日从多个城市背景中稳定抽取一个事件；
- 按世界种子、候选池版本和日期使用可复现选择，同一存档重复准备不会改变结果或重复写入；
- 保持事件键、类别、状态和关联角色经过规则校验，并让重复准备保持幂等；
- 根据实际游玩反馈继续调整事件密度、角色反应和原版风格，逐步扩展社区事件与跨日影响。

## 阶段 27：LLM 城市事件候选（已完成）

- 允许支持该能力的 provider 为每天提出最多三个公共城市事件候选；
- 候选严格通过事件键、类别、状态、文字长度和关联角色校验后才可进入世界；
- 候选、稳定选择结果和最终事件使用 SQLite 元数据与事件账本幂等保存；
- provider 不可用、返回错误或校验失败时回退到阶段 26 的代码事件池；
- 记录生成开始、结束、错误和回退耗时，不记录提示词、响应正文或密钥。

## 阶段 28：城市事件驱动对白与对话记录（已完成）

- 将当天已经持久化的公共城市事件作为只读上下文，加入角色故事和开店前对白的生成前提；
- 保持角色故事事件、剧情游标、金钱和关系等权威状态不被公共事件上下文改写；
- 生成失败时继续使用本地对白回退，且没有公共事件时保持原有行为；
- 对每个已展示场景按营业日、场景和台词顺序记录对白，使用幂等收据避免重复写入；
- 不记录 API Key、提示词全文或 provider 的原始响应，并继续保留原版音乐、休息、保存和房间切换边界。

## 阶段 29：跨日记忆对白提示（已完成）

- 将角色私有记忆按当前角色的可见性、时间和数量限制加入对白生成前提；
- 保留亲历、听说、传闻、推断等来源标记，让模型知道记忆的可信程度和距离；
- 记忆只作为只读对白线索，不得直接改变金钱、关系、事件或剧情游标；
- 继续使用本地回退和幂等记录，避免记忆提示失败影响营业流程。

## 阶段 30：后台预生成与性能优化（已完成）

- 当天进入酒吧只建立本地故事骨架和本地事件，不同步等待 LLM；
- 可选地在后台最多预生成下一营业日的城市事件和完整故事图；
- 后台结果按日期、世界种子和生成版本幂等保存，下一天直接复用；
- provider 超时或失败时回退到阶段 26 的本地事件和对白，不能影响当前营业日；
- 后台线程使用 daemon 运行，无法安全中断的网络请求不会阻塞进程退出；
- 记录后台开始、就绪、回退和错误耗时，并继续更新安装配置和架构说明。

## 阶段 31：连续营业稳定性与诊断收口（进行中）

- 用连续多日回归测试验证城市事件、角色记忆、对白记录、故事游标和 SQLite 存档可以一起跨日衔接；
- 验证后台预生成完成时会被下一营业日复用，未完成、超时或失败时仍能即时进入本地回退流程；
- 提供只读的 `diagnose-world` 检查命令，从保存的 SQLite 世界库和可选 JSONL 日志生成脱敏诊断/回放报告；
- 报告按营业日列出事件、已展示对白、角色记忆、故事图生成状态、进度游标和后台 timing，不执行 provider 请求，也不修改存档；
- 继续检查原版音乐选择、中场休息、保存页面和房间切换边界；
- 不在本阶段构建新的 Preview 或修改已发布版本。

## 阶段 32：原版风格对白质量（进行中）

- 继续以原版营业节奏和角色语气作为对白生成约束；
- 拒绝同一角色在同一场景中重复较长的逐字台词，避免模板化对话；
- 保持对白长度、说话人、立绘和调酒行为边界校验；
- 为连续营业、事件回顾和角色记忆增加自然度回归测试；
- 本阶段先优化生成质量，不构建新的 Preview。

## 阶段 33：对白与事件兼容性修复（进行中）

- 兼容 DeepSeek 事件响应的常见 JSON transport envelope，同时保持严格语义校验和脱敏错误诊断；
- 让顾客点单可以自然表达甜、女性化/漂亮、冰多、带劲等偏好，并保持原生调酒规则和可验证结果；
- 让本地 fallback 离场对白按角色和场景身份稳定变化，减少模板化重复；
- 聚焦测试和完整测试通过，不破坏调酒规则、原版流程或存档边界。

## 阶段 34：连续营业稳定性与诊断收口（计划）

对应阶段 31 尚未完全收口的部分。

- 连续 DAY1、DAY2、DAY3 及更多天的自动回归；
- 城市事件、角色记忆、对白记录和剧情游标一起跨日保存；
- 覆盖后台预生成成功、失败、超时三种情况；
- 验证 `diagnose-world`、`timing.log` 和 `dialogue.log` 的一致性；
- 验证存档、读档、重启后世界状态不回退；
- 完成标准：连续多日测试通过、provider 失败仍可安全进入游戏、诊断报告能解释一天发生了什么；不构建新的公开版本。

## 阶段 35：原版流程与对白风格收口（计划）

对应阶段 32 尚未完全收口的部分。

- 对照原版开店前、顾客到店、调酒、中场和收尾节奏；
- 检查 Jill 与顾客的说话比例、说话人立绘匹配和角色身份边界；
- 减少系统提示感、模板化句式和空泛收尾，让对白围绕事件、关系和当日情境展开；
- 使用原版资料作为研究依据，但不复制原版大段台词；
- 完成标准：每个场景有明确对白结构，并具备对白质量回归测试。

## 阶段 36：角色 Agent 记忆与关系深化（计划）

- 增加角色长期目标、短期目标和关系变化原因；
- 允许角色对同一事件拥有不同理解，并处理记忆重要性、时效性和冲突；
- 保持角色信息隔离，角色只看到自己应该知道的信息；
- 让记忆影响点单、话题和回应，但不得越权修改金钱、事件或剧情游标；
- 完成标准：多角色视角、跨日记忆和信息隔离测试通过。

## 阶段 37：多日城市事件链（计划）

- 让事件经历传闻、发展、解决或留下后果等生命周期；
- 支持事件影响多个营业日，并让不同角色产生不同反应；
- 支持事件被忽略、误解或延后处理；
- LLM 只提出候选，规则层负责事件状态转换；
- 完成标准：至少一条跨三天事件链可追踪，重启/读档/重复准备不重复推进，无 API 时仍有本地回退。

## 阶段 38：顾客安排与调酒表达扩展（计划）

- 支持顾客按甜度、酒精强度、冰量、口感、颜色或风格描述需求；
- 支持同一角色在不同情绪下使用不同表达，并增加点单歧义和澄清场景；
- 保留原版调酒判定，确保自然语言只映射到可验证规则订单；
- 完成标准：自然描述稳定映射、错误订单按原版规则结算、点单文本与结果可追踪。

## 阶段 39：存档、升级与实例隔离强化（计划）

- 完善版本升级时的数据库迁移、旧版本存档配对和实例版本校验；
- 强化安装目录、数据库、日志和 API Key 的版本隔离；
- 提供失败升级的恢复路径，确保多个预览版本互不覆盖；
- 完成标准：迁移可重复执行、失败不破坏原存档，安装器和诊断工具能显示实例版本。

## 阶段 40：正式版本候选与发布准备（计划）

- 完成 Windows x64 全新安装、多日真实游戏、升级、卸载和读档验收；
- 完成公开包内容审计、Steam 原版哈希和补丁契约复核；
- 同步发布说明、README 和社区更新文案；
- 完成标准：关键功能具备自动测试和真实游戏证据，发行包不含 UTMT、原版 `data.win`、源代码、数据库或 API Key，再决定是否发布下一版本。

## 阶段交付规则

- 一个阶段对应一个独立 PR；
- 每个 PR 只解决一个完整主题，包含相关代码、测试、必要文档、验收标准、测试结果和未解决风险；
- 不把多个不相关功能塞进同一个 PR；
- 当前阶段完成并经过 Review 后，才进入下一阶段；
- 阶段 34 以后不提前创建实现对话，避免多个阶段同时修改同一批文件。
